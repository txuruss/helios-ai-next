# Helios AI Lead Capture & Dashboard Schema

Source file for the Helios AI Client Delivery & Systems project. Defines the standard fields Helios AI collects, saves, and displays inside a client lead dashboard — for salons, spas, nail salons, barbershops, dentists, wellness clinics, med spas, gyms, and other local service businesses.

---

## 1. Purpose

Every Helios AI install captures leads from chat, WhatsApp, forms, and manual entry into **one consistent record shape**. This file is the single source of truth for:

- Which fields are required vs optional
- How statuses, follow-ups, priorities, and sources are named and used
- What the dashboard table and detail view show
- Validation, duplicate handling, and example records

Companion file: `Helios AI Owner Notification Templates.md` — notifications are generated from the fields defined here. The two files must stay consistent.

The schema is deliberately **MVP-simple**: every field earns its place by helping the business respond faster or follow up better. It is structured (stable keys, defined enums, ISO dates) so future upgrades — live calendar booking, analytics, multi-location — extend it without renaming anything.

---

## 2. Core Lead-Capture Philosophy

1. **Capture a contact method first.** A conversation without a phone number, email, or messageable handle is not a lead — the assistant's first capture priority is always a way to reach the person.
2. **Appointment requests before live booking.** The MVP flow is: customer states service + preferred date/time → business confirms manually. Live calendar booking is a later upgrade, never a launch requirement.
3. **Ask only what the assistant needs.** Three good fields collected in a natural conversation beat ten fields in an interrogation. Everything beyond name + contact + interest is optional.
4. **Store the customer's words.** Summaries are useful; verbatim messages are evidence. Keep both, clearly separated.
5. **Never invent data.** Empty means empty. No guessed emails, no assumed services, no fabricated dates.
6. **Every lead has exactly one status** at all times, and the status answers: "what is the next thing that should happen?"
7. **The dashboard is the system of record.** Notifications are pointers; the lead record holds the truth.

## 3. Required Lead Fields

Every lead record must have these — the system should not save a lead without them:

| Field Key | Label | Type | Rule |
|---|---|---|---|
| `id` | Lead ID | UUID | Generated by the system |
| `customer_name` | Customer Name | text | Use `Unknown` if not captured — never blank |
| *(contact)* | — | — | **At least one of** `phone`, `email`, or `social_handle` must be present |
| `inquiry_source` | Inquiry Source | enum | One of the sources in section 8 |
| `lead_status` | Lead Status | enum | Defaults to `New` (section 16) |
| `created_at` | Created At | timestamp | Set by the system, business local timezone displayed |

---

## 4. Optional Lead Fields

Everything in sections 5–13 that is not listed in section 3 is optional. Optional fields are:

- Collected only when the conversation naturally produces them
- Displayed only when present (no empty rows in the detail view)
- Never required to save the record

If a client wants a new field, add it as optional first; promote to required only after a month of real use proves it is always collectable.

## 14. Dashboard Table Columns

The main lead table shows these columns, in this order (MVP):

| # | Column | Source Field | Notes |
|---|---|---|---|
| 1 | Customer | `customer_name` | Bold; `Unknown` shown dimmed |
| 2 | Contact | `phone` / `email` | Show the preferred/first available method |
| 3 | Service | `service_requested` | Truncated |
| 4 | Source | `inquiry_source` | Badge |
| 5 | Status | `lead_status` | Colored badge (section 16) |
| 6 | Follow-Up | `follow_up_status` + `follow_up_due_date` | Highlight when due/overdue |
| 7 | Preferred Time | `preferred_date` + `preferred_time` | Only for appointment requests |
| 8 | Received | `created_at` | Relative + exact on hover |

Optional columns for clients with teams: Assigned To. Keep the table at 8 or fewer columns on small screens — everything else lives in the detail view.

Default sort: newest first. Leads with `lead_status = New` or `Needs Review`, or an overdue follow-up, are visually emphasized.

## 15. Dashboard Detail View Fields

Opening a lead shows, grouped in this order:

1. **Header** — `customer_name`, status badge, priority badge, `created_at`
2. **Next action** — `recommended_next_action` (most prominent element on the page)
3. **Contact** — phone, email, social handle, preferred contact method, language
4. **Request** — service requested, category, new customer flag, appointment fields (preferred/confirmed times, notes)
5. **Conversation** — summary, last customer message (verbatim), link to full transcript
6. **Tracking** — status history (status, changed by, when), follow-up status + dates + count
7. **Assignment** — assigned to, location (if applicable)
8. **Internal notes** — newest first, with author + timestamp, plus the add-note box
9. **Record info** — lead ID, source detail, duplicate-merge history if any

Empty optional fields are hidden, not shown as blanks.

## 16. Lead Status Definitions

Exactly one status per lead. Allowed values, exact spelling:

| Status | Meaning | Typical Next Action |
|---|---|---|
| `New` | Just captured; nobody has reviewed it | Review and respond |
| `Needs Review` | Captured but ambiguous/incomplete; human judgment needed | Read conversation, decide response |
| `Contacted` | Business has responded at least once | Await reply; set follow-up |
| `Awaiting Reply` | Ball is in the customer's court | Follow up if silent past the window |
| `Appointment Requested` | Customer asked for a specific service/time; not yet confirmed | Confirm or propose alternative |
| `Appointment Confirmed` | Business confirmed a date & time | Send reminder; deliver service |
| `No Response` | Customer went silent after the follow-up policy completed | None; revisit in a re-engagement pass |
| `Closed Won` | Customer booked/purchased | Optional: ask for review/rebooking |
| `Closed Lost` | Customer explicitly declined or went elsewhere | None; record reason in notes |
| `Archived` | Removed from active views (spam, test, duplicate) | None |

Normal lifecycle: `New` → `Contacted` → `Awaiting Reply` → `Appointment Requested` → `Appointment Confirmed` → `Closed Won`. Any status may move to `Closed Lost`, `No Response`, or `Archived`. Status changes are manual or assistant-set, always logged with who/when.

---

## 17. Follow-Up Status Definitions

| Status | Meaning |
|---|---|
| `Not Started` | No follow-up considered yet (default for fresh leads) |
| `Follow-Up Needed` | A follow-up should be sent; `follow_up_due_date` says when |
| `Follow-Up Sent` | At least one follow-up sent; awaiting outcome |
| `Waiting On Customer` | Customer promised an answer ("I'll check my schedule") |
| `Completed` | Follow-up loop ended in an outcome (booked, declined) |
| `No Follow-Up Needed` | Lead resolved on first contact or follow-up is inappropriate |

---

## 18. Priority Status Definitions

| Priority | Meaning | Examples |
|---|---|---|
| `Urgent` | Respond immediately; revenue or reputation at risk now | Same-day request, pain/discomfort, complaint |
| `High` | Respond today | Appointment request, event-driven need ("before Saturday") |
| `Normal` | Respond within the agreed window (default 4 business hours) | Standard inquiry with contact details |
| `Low` | No time pressure | General question, price browsing without contact urgency |

Priority affects notification routing (see the Owner Notification Templates file) and dashboard emphasis. Default is `Normal`; the assistant may raise to `Urgent`/`High` only on explicit signals in the customer's own words.

## 19. Data Validation Rules

- **Contact requirement:** reject saves with no `phone`, `email`, or `social_handle` (log as a conversation, not a lead).
- **Phone:** store digits + leading `+` country code where known; display formatted. Minimum 7 digits to count as a contact method.
- **Email:** must match a basic `name@domain.tld` shape; otherwise store in notes, not in `email`.
- **Dates:** `preferred_date`, `follow_up_due_date` are ISO `YYYY-MM-DD`; timestamps are ISO 8601 with timezone. Ambiguous spoken dates stay in `preferred_date_text` until resolved.
- **Enums:** `lead_status`, `follow_up_status`, `priority`, `inquiry_source` accept only the exact values defined in this file. Unknown inbound values map to `Needs Review` / `Not Started` / `Normal` / `Other` respectively — never invent new enum values silently.
- **Text limits:** `customer_name` ≤ 120 chars; `service_requested` ≤ 200; `last_customer_message` ≤ 500 (truncate with `…`); `conversation_summary` ≤ 400; notes ≤ 2,000 per entry.
- **Trim everything**; strip control characters; never store raw HTML.
- **Defaults:** `lead_status = New`, `follow_up_status = Not Started`, `priority = Normal`, `follow_up_count = 0`, `appointment_requested = false`.

## 20. Duplicate Lead Handling Rules

A new capture is a **suspected duplicate** when, within the last 30 days, an existing lead matches by (in order of confidence):

1. Same normalized phone digits, or
2. Same lowercased email, or
3. Same `customer_name` + same `inquiry_source`

Handling:

- **Same conversation continuing** (same channel, within 7 days): do **not** create a new lead. Append to the existing record — update `last_customer_message`, `conversation_summary`, and re-open status if it was `No Response`.
- **New request from a known customer** (e.g. booked last month, asking again): create a **new lead**, tag both records `repeat-customer`, and link them in notes. Repeat business is a new opportunity, not a duplicate.
- **True accidental duplicate** (double form submit): keep the record with the earliest `created_at`, merge any extra detail into it, mark the other `Archived` with note `Duplicate of {lead id}`.
- **Never hard-delete** lead records; archive instead.
- When unsure, keep both and set the newer one to `Needs Review` — a human decides.

## 24. Recommended Dashboard Views

| View | Filter | Purpose |
|---|---|---|
| **Today / Inbox** (default) | `lead_status` in `New`, `Needs Review` + follow-ups due today or overdue | The "do this now" list |
| **Appointment Requests** | `lead_status = Appointment Requested` | Confirm or propose times |
| **Awaiting Reply** | `lead_status` in `Contacted`, `Awaiting Reply` | Watch for silence past the window |
| **Follow-Ups Due** | `follow_up_status = Follow-Up Needed` and `follow_up_due_date <= today` | Daily follow-up pass |
| **Confirmed Upcoming** | `lead_status = Appointment Confirmed`, `confirmed_datetime >= now` | Tomorrow's schedule at a glance |
| **All Leads** | Everything except `Archived` | Search and browse |
| **Closed** | `Closed Won`, `Closed Lost`, `No Response` | Outcomes; source of weekly numbers |

Each view supports filtering by `inquiry_source` and (where used) `assigned_to`. MVP needs only Today, Appointment Requests, Follow-Ups Due, and All Leads — add the rest as the client grows.

## 25. Admin Notes and Internal Comments

- Every note entry stores **author, text, and timestamp**; displayed newest first.
- Notes are append-only — correct mistakes with a new note, do not edit history.
- Notes are internal only: never shown to customers, never auto-inserted into outgoing messages.
- Use notes for: call outcomes, special requests, no-show history, duplicate-merge records, status-change reasons (especially `Closed Lost`).
- Keep operational facts in fields, judgments in notes. ("Prefers Saturdays" → note; "preferred_date: 2026-06-13" → field.)
- Tags are for filtering (`vip`, `price-sensitive`, `repeat-customer`); keep the tag list short and consistent per client — review during monthly optimization.

Run before launch for every client, and re-check during monthly system checks:

- [ ] A test lead from **each installed channel** creates exactly one record with the correct `inquiry_source`

## 27. How Helios AI Should Use This File

When building, configuring, or reviewing any client's lead capture or dashboard:

1. **Use these exact field keys, enum values, and spellings.** Do not invent new statuses, sources, or fields per client — extend this file first if a real need appears.
2. **Enforce the required/optional split** from sections 3–4: never block a lead on optional data, never save one without the required core.
3. **Default to the appointment-request flow** (request → manual confirm). Recommend live calendar booking only as a later upgrade once the request flow runs smoothly.
4. **Apply validation (19) and duplicate rules (20)** in any capture logic you design or review.
5. **Generate dashboards from sections 14–15 and 24** — MVP views first; add views only when the client's volume justifies them.
6. **Keep notifications consistent**: anything that fires a notification must reference fields and statuses defined here, using the templates in `Helios AI Owner Notification Templates.md`.
7. **Use the example records (22–23)** as the shape for test data during QA — clearly fictional, never presented as real client data.
8. **Run the section-26 checklist** at launch and during every monthly system check; log results in the client's delivery record.
9. When a client requests schema changes, prefer: optional field → tag → note, in that order, before adding required structure. Simplicity is a feature.
